# Role-owned menus (`role_menu`) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A role stores its own menu list; users follow it live; the role screen ticks menus one by one so Tickets and Communication are independent.

**Architecture:** New `role_menu` table mirrors `user_menu_grants` (company-owned, CRUD flags). Effective menus for a user = union of `role_menu.can_read` over their active roles, minus `user_menu_grants` denials. Served via `GET /menu-grants/me` as `allowedMenus`. Frontend sidebar uses it for custom-role users only; built-in-role nav is untouched. Role-menu writes also keep module permissions in sync so APIs keep working.

**Tech Stack:** Spring Boot 3 / Java / JPA / Flyway (MySQL 8), JUnit5 + Mockito; Angular (signals, OnPush), vitest.

**Spec:** `docs/superpowers/specs/2026-11-19-role-menu-design.md`

## Global Constraints

- Next Flyway version is `V149`; latest existing is `V148`. Commit migrations in version order.
- FKs point at `company_roles.id` and `menu_items.id`, never `companies.id` (see memory companies-table-dual-id-columns).
- Do NOT put menu codes in the JWT (admin JWT ~7.5 KB; 8 KB header limit). Fetch via `/menu-grants/me`.
- `menu_items.code` equals the frontend nav node `id`.
- `user_menu_grants` stays deny-only; no per-user additive menus.
- Backend `@PreAuthorize` module guards are unchanged (spec non-goal).
- Built-in roles' nav (`roles:` arrays in `navigation.config.ts`) is unchanged.
- Verify on :8082 (profile `local`, `DB_PORT=3306`) and :4300 only; never touch real backend port or :4200. Keep test rows in the dev DB.
- Write caveman-free normal code/commits. Commit messages end with the attribution lines from the session reminder.

## Review Focus

1. A role with **no** `role_menu` rows (newly created): custom-only user sees only public nodes (Dashboard), not a crash or "everything".
2. `/menu-grants/me` fetch fails: sidebar falls back to current behaviour (does not blank the menu).
3. A user holding **two** roles: menus are the union; removing one role's menu keeps it if the other role has it.
4. A menu denied for one user in `user_menu_grants` is hidden for that user even if the role holds it, and only for that user.
5. Role save that would strip a module permission still needed by another ticked menu of the same role, or `ROLE_UPDATE` from the last admin role: must keep it / be refused.
